## Адресация

- Туннель tap: **10.99.0.0/24** (сервер .1, клиент .2)
- Офис 1 (клиент), как его видит офис 3: 172.16.3.0 без изменений, **172.16.11.0 → 172.16.211.0**, **172.16.12.0 → 172.16.212.0**
- Офис 3 (сервер), как его видит офис 1: 172.16.1.0 без изменений, **172.16.11.0 → 172.16.111.0**, **172.16.12.0 → 172.16.112.0**

Мост tap0+eth0 из методички делать нельзя: из-за одинаковых сетей L2 не объединить. Вместо него tap с отдельной транзитной подсетью, маршрутизацией и NETMAP (NAT 1:1). Скрипт angristan тоже не подходит: он ставит tun, а нужен tap.

## 1. FW-Linux-1 (офис 3)

1. Проброс порта: `iptables -t nat -A PREROUTING -i eth0 -p udp --dport 1194 -j DNAT --to <IP OpenVPN-L2-Server>`
2. Разрешить FORWARD на udp/1194 к серверу. - `iptables -I FORWARD 1 -i eth0 -o eth1 -p udp -d <IP OpenVPN-L2-Server> --dport 1194 -j ACCEPT`
3. Статические маршруты: `172.16.3.0/24`, `172.16.211.0/24`, `172.16.212.0/24` через IP сервера в 172.16.1.0/24.
	1. ip route add 172.16.3.0/24 via 172.16.1.12
	2. ip route add 172.16.211.0/24 via 172.16.1.12
	3. ip route add 172.16.212.0/24 via 172.16.1.12
4. Включить `ip_forward` и сохранить правила.

## 2. OpenVPN-L2-Server (офис 3)

1. Подготовка и пакеты: `openvpn easy-rsa` (bridge-utils не нужен). Проверить выход в интернет.
2. PKI: CA, сертификат сервера, `dh`, `ta.key`, сертификат `client1` (как в методичке). Если нет команд easy-rsa 2, использовать easy-rsa 3.
	1. ```bash
	   make-cadir ~/openvpn-ca 
	   cd ~/openvpn-ca 
	   ls
	   
	   ./easyrsa init-pki 
	   ./easyrsa build-ca nopass # Common Name: любое, например OpenVPN-CA 
	   ./easyrsa build-server-full server nopass 
	   ./easyrsa gen-dh 
	   openvpn --genkey secret ta.key # на OpenVPN 2.5+ синтаксис: openvpn --genkey secret ta.key 
	   ./easyrsa build-client-full client1 nopass
	   ```
3. `/etc/openvpn/server.conf`:
    - `dev tap0`, `proto udp`, `port 1194`, `server 10.99.0.0 255.255.255.0`
    - `client-config-dir ccd`, плюс файл `ccd/client1` со строкой `ifconfig-push 10.99.0.2 255.255.255.0`
    - пути к ca, cert, key, dh, tls-auth
    - **убрать** `secret static.key` и все `push redirect-gateway/dhcp-option`
   ```bash
   # nano /etc/openvpn/server.conf
   local <IP сервера в 172.16.1.0/24>
port 1194
proto udp
dev tap
server 10.99.0.0 255.255.255.0
client-config-dir ccd

ca ca.crt
cert server.crt
key server.key
dh dh.pem            # для easy-rsa 2: dh2048.pem
tls-auth ta.key 0

keepalive 10 120
user nobody
group nogroup
persist-key
persist-tun
status openvpn-status.log
verb 3

mkdir /etc/openvpn/ccd
echo "ifconfig-push 10.99.0.2 255.255.255.0" > /etc/openvpn/ccd/client2
# Имя файла `client1` должно совпадать с Common Name сертификата клиента.
cd ~/openvpn-ca 
cp ta.key /etc/openvpn/
cp pki/ca.crt /etc/openvpn/ 
cp pki/issued/server.crt /etc/openvpn/ 
cp pki/private/server.key /etc/openvpn/
cp pki/dh.pem /etc/openvpn/

echo 'net.ipv4.ip_forward=1' >> /etc/sysctl.conf && sysctl -p
systemctl start openvpn@server
systemctl status openvpn@server
ip a show tap0
   ```
4. `ip_forward=1`. UFW и MASQUERADE из методички не использовать.
5. Маршруты через клиента: `ip route add 172.16.3.0/24 via 10.99.0.2`, то же для `172.16.211.0/24` и `172.16.212.0/24`. Сделать их постоянными.
	1. ip route add 172.16.3.0/24 via 10.99.0.2 dev tap0
	2. ip route add 172.16.211.0/24 via 10.99.0.2 dev tap0
	3. ip route add 172.16.212.0/24 via 10.99.0.2 dev tap0
6. NETMAP, для каждой из сетей 11 и 12 (212 для 12):
    - iptables -t nat -A POSTROUTING -o tap0 -s 172.16.11.0/24 -j NETMAP --to 172.16.111.0/24
    - iptables -t nat -A PREROUTING  -i tap0 -d 172.16.111.0/24 -j NETMAP --to 172.16.11.0/24
    - iptables -t nat -A POSTROUTING -o tap0 -s 172.16.12.0/24 -j NETMAP --to 172.16.112.0/24
    - iptables -t nat -A PREROUTING  -i tap0 -d 172.16.112.0/24 -j NETMAP --to 172.16.12.0/24
7. Разрешить FORWARD, запустить `openvpn@server`, проверить `ip a show tap0`.
	1. iptables -A FORWARD -i tap0 -j ACCEPT
	2. iptables -A FORWARD -o tap0 -j ACCEPT
	3. systemctl restart openvpn@server 
	4. systemctl status openvpn@server
	5. systemctl enable openvpn@server
	6. ip a show tap0
8. Собрать `client2.ovpn` (скриптом `make_config.sh`) и передать на клиента через `scp`.
```bash
mkdir -p ~/client-configs/files
nano ~/client-configs/make_config.sh

#!/bin/bash
# Использование: ./make_config.sh client2
CA=~/openvpn-ca/pki/ca.crt
CRT=~/openvpn-ca/pki/issued/${1}.crt
KEY=~/openvpn-ca/pki/private/${1}.key
TA=~/openvpn-ca/ta.key
OUT=~/client-configs/files/${1}.ovpn

cat > $OUT <<EOF
client
dev tap
proto udp
remote 192.168.1.2 1194
nobind
persist-key
persist-tun
remote-cert-tls server
key-direction 1
verb 3
<ca>
$(cat $CA)
</ca>
<cert>
$(openssl x509 -in $CRT)
</cert>
<key>
$(cat $KEY)
</key>
<tls-auth>
$(cat $TA)
</tls-auth>
EOF

chmod 700 ~/client-configs/make_config.sh
cd ~/client-configs
./make_config.sh client2
ls -l files/

# На клиенте: 
scp root@192.168.1.2:/root/client-configs/files/client2.ovpn /root/
```

Перед тем, как копировать, надо разрешить SSH на Linux-FW-1:
```bash
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 22 -j DNAT --to 172.16.1.12
iptables -A FORWARD -i eth0 -o eth1 -p tcp -d 172.16.1.12 --dport 22 -j ACCEPT

# На openvpn-сервере и фаерволе
nano /etc/ssh/sshd_config - разрешить вход root
```

## 3. pfSense-FW-3 (офис 1)

1. Static Routes (через шлюз OpenVPN-L2-Client в 172.16.3.0/24): `172.16.1.0/24`, `172.16.111.0/24`, `172.16.112.0/24`.
2. Firewall rules на LAN-интерфейсах: разрешить трафик в эти сети. Включить System → Advanced → Firewall & NAT → «Bypass firewall rules for traffic on the same interface» (асимметрия).
3. Проверить, что `192.168.1.2` (внешний IP FW-Linux-1) пингуется из 192.168.3.0/24.

## 4. OpenVPN-L2-Client (офис 1)

1. Пакеты: `openvpn` (для GUI ещё network-manager-openvpn).
2. Положить `client2.ovpn`. Правки: `client`, `dev tap`, `proto udp`, `remote 192.168.1.2 1194`, ca/cert/key/tls-auth. **Удалить** `ifconfig 10.1.0.2…` и `secret static.key`.
3. `ip_forward=1`.
4. Подключиться, получить 10.99.0.2 на tap0.
5. Маршруты: `ip route add 172.16.1.0/24 via 10.99.0.1`, то же для `172.16.111.0/24` и `172.16.112.0/24`.
6. NETMAP, для сетей 11 и 12 (112 для 12):
    - `iptables -t nat -A POSTROUTING -o tap0 -s 172.16.11.0/24 -j NETMAP --to 172.16.211.0/24`
    - `iptables -t nat -A POSTROUTING -o tap0 -s 172.16.12.0/24 -j NETMAP --to 172.16.212.0/24`
    - `iptables -t nat -A PREROUTING -i tap0 -d 172.16.211.0/24 -j NETMAP --to 172.16.11.0/24`
    - `iptables -t nat -A PREROUTING -i tap0 -d 172.16.212.0/24 -j NETMAP --to 172.16.12.0/24`
7. Разрешить FORWARD, сохранить правила и маршруты.
	1. iptables -A FORWARD -i tap0 -j ACCEPT 
	2. iptables -A FORWARD -o tap0 -j ACCEPT

2. Из 172.16.3.x ping в 172.16.1.x. Из 172.16.11.x и 172.16.12.x ping в 172.16.211.x, 172.16.212.x и 172.16.1.x.
3. Обратное направление: из офиса 3 в 172.16.3.x, 172.16.111.x и 172.16.112.x.
4. Если не ходит: `tcpdump -i tap0` на обоих узлах и `iptables -t nat -L -n -v` для счётчиков.

# Мои проблемы

1. Не работает интернет на vlan'овских машинах, а точнее - не работает даже пинг до 8.8.8.8. Скорее всего надо разобраться с правилами в фаерволлах, и тогда все будет работать.
2. Не работает пинг по сетям vlan - vlan. Скорее всего, трассировка покажет мне в хопах нужные адреса, просто правила фильтрации на фаерволлах немного косячные.

Linux-FW-1:
```bash
iptables -I INPUT 1 -i ens4+ -j ACCEPT
iptables -I FORWARD 2 -i ens4.11 -o ens3 -s 172.16.11.0/24 -j ACCEPT
iptables -I FORWARD 2 -i ens4.12 -o ens3 -s 172.16.12.0/24 -j ACCEPT
iptables -t nat -A POSTROUTING -s 172.16.11.0/24 -o ens3 -j MASQUERADE
iptables -t nat -A POSTROUTING -s 172.16.12.0/24 -o ens3 -j MASQUERADE
```

pfSense-FW-1:
- Интерфейсы OPT1 и OPT2
  Action - PASS
  Interface - OPT1/OPT2
  Protocol - Any
  Source - Network -> 172.16.11.0 / 172.16.12.0
  Destination - Any
- Outbound NAT (аналог Masquerade)
  Firewall - NAT - outbound. - **Automatic** (по умолчанию): pfSense сам делает NAT для всех подсетей на своих интерфейсах, включая VLAN. Менять ничего не нужно. Проверь, что в списке автоматических правил есть `172.16.11.0/24` и `172.16.12.0/24`.
  
**Теперь вторая проблема**.
Firewall - Rules - NAT - LAN:
Action - PASS
Protocol - any
Source - Address of Alias - OFFICE1_NETS
Destination - any

То, что в трассировке нет хопов с адресами 10.99.0.0 - так и должно быть. Поскольку прописан NETMAP, то к адресу точки туннеля и соседнего фаервола применяется обратная трансляция и их адреса подставляются в виртуальный адрес назначения (из сети 212 например). 

Чтобы не было звездочек в трассировке, на Linux-FW, сервере и клиенте прописать это:
```bash
sysctl -w net.ipv4.icmp_ratelimit=0
echo 'net.ipv4.icmp_ratelimit=0' >> /etc/sysctl.conf
```

Команда для трассировки:
```bash
traceroute -I -N 1 172.16.212.11
```

**Kali → 172.16.212.11 (хоп 10.99.0.2 пропал).**  
Адрес 212.11 виртуальный. Клиент в PREROUTING на tap0 меняет назначение 212.11 → 12.11 (DNAT), и это попадает в запись conntrack. Когда узел после этой точки шлёт «time exceeded», ядро связывает ошибку с этой записью и при обратной трансляции подставляет в источник ответа исходное назначение, то есть 172.16.212.11. Так хопы после DNAT выглядят как 212.11. Скорее всего, это и есть хоп 3, где должен быть клиент.

**Debian 172.16.11.10 → 172.16.3.10 (хоп 10.99.0.2 виден).**  
172.16.3.10 реальный адрес, и DNAT для него не применяется. Транслируется только источник (11 → 111 на сервере), а при обратной трансляции ошибки подменяется получатель, а не источник. Поэтому клиент отвечает своим настоящим адресом 10.99.0.2.
