# Действие 2 - настройка GRE на Cisco

R1
```text
interface Tunnel1
description "GRE-Tunnel1"
interface Tunnel1
ip address 172.10.100.1 255.255.255.252
ip mtu 1400
ip tcp adjust-mss 1360
tunnel source e0/1
tunnel destination 10.10.30.4
do wr
```

R4
```text
interface Tunnel1
ip address 172.10.100.2 255.255.255.252
ip mtu 1400
ip tcp adjust-mss 1360
tunnel source e0/0
tunnel destination 172.10.100.1
do wr
```

Еще надо добавить accept-правила на обоих роутерах, потому что действует политика default deny. Команда:
```bash
sudo iptables -I INPUT 1 -s 192.168.1.0/24 -j ACCEPT
```
Можно и для всех сетей конечно добавить, но лучше только для сетей, которые должны общаться непосредственно через GRE

```text
router ospf 1
network 172.10.100.0 0.0.0.3 area 0
do wr
```

### Действие 4 - настроить GRE между линуксами в сетям 172.16.2.0 и 172.16.4.0

```bash
modprobe ip_gre
lsmod | grep gre
```

должно получиться такое:
```bash
ip_gre [цифры] 0
gre [цифры] 1 ip_gre
```

На дистрибутиве должны быть установлены iptables и iproute2

Далее настраиваем туннель:
```bash
nano /etc/sysctl.conf
# раскомментировать либо прописать net.ipv4.ip_forward=1
# ctrl-o + ctrl-x
sysctl -p
# вывод - net.ipv4_ip_forward=1

sudo ip tunnel add gre1 mode gre ttl 255 local 172.16.2.12 remote 172.16.4.12
```

Чтобы это все сохранить, нужна работа с /etc/network/interfaces. На узлах указываем endpoint как адрес wan фаерволла второй точки туннеля
```bash
# The gre1 tunnel interface
auto gre1
iface gre1 inet manual
	mode gre
	local 172.16.2.14
	endpoint 192.168.4.2
	ttl 255
	mtu 1400
	address 172.10.102.1/30
```

И еще `nano /etc/modules`:
```bash
modprobe ip_gre
```

Настраиваем NAT на фаерволлах. Будем, например, 172.16.4.13 на 192.168.4.2 (SNAT на Linux-FW-2), а дальше фаерволл pfSense-FW-2 сам разберется по DNAT'у, куда его направить.

**Что сделать:**
1. **Межсетевые экраны.**
    - pfSense: правило Firewall на WAN, разрешающее протокол GRE. Port Forward с протоколом GRE, назначение = WAN-адрес pfSense, редирект на GRE-Linux-Client.
    - Linux-FW-2:
        ```
        iptables -t nat -A PREROUTING -i <wan> -p gre -j DNAT --to <IP GRE-Linux-SRV>  
        iptables -A FORWARD -p gre -j ACCEPT  
        ```
2. **Туннель на GRE-Linux-Client.** В `remote` указывается внешний адрес экрана другой стороны, а не адрес самого сервера:
    ```
    ip tunnel add gre1 mode gre local <свой IP> remote <WAN Linux-FW-2> ttl 255
    ip addr add 172.10.102.1/30 dev gre1
    ip link set gre1 up
    ```
3. **Туннель на GRE-Linux-SRV.** Всё так же, но `remote <WAN pfSense>` и адрес `172.10.102.2/30`.
4. **Маршруты внутрь туннеля.**
    - На клиенте: `ip route add 172.16.2.0/24 via 172.10.102.1`
    - На сервере: `ip route add 172.16.4.0/24 via 172.10.102.2`
    - На обоих узлах: `sysctl -w net.ipv4.ip_forward=1`
5. **Маршруты в локальных сетях.** Хостам сетей 172.16.4.0/24 и 172.16.2.0/24 нужен маршрут в удалённую сеть через свой GRE-узел. Обычно его задают на самих экранах (pfSense: System → Routing → Static Routes) или на хостах. Проверьте, что правила фильтрации разрешают трафик между этими сетями.

Туннель по-прежнему устанавливается между двумя Linux-узлами. Адрес `remote` задаёт только то, куда отправить внешний (транспортный) IP-пакет, в который упакован GRE.

Узлы стоят за NAT, и их адреса приватные. Из другой сети до них не добраться: промежуточные маршрутизаторы такие адреса не маршрутизируют. Достижимы только внешние адреса экранов. Поэтому путь пакета такой:

1. GRE-Linux-Client шлёт пакет с `dst = WAN Linux-FW-2`.
2. Пакет доходит до Linux-FW-2. Правило DNAT (`-p gre`) меняет `dst` на внутренний адрес GRE-Linux-SRV.
3. GRE-Linux-SRV получает пакет и распаковывает его. Для него это обычный GRE от клиента.

Ответные пакеты идут так же в обратную сторону. Экран клиента подменяет `src` на свой WAN-адрес (SNAT/masquerade) при отправке и делает DNAT на клиента при приёме.

Поэтому проброс GRE на экранах и нужен: без него экран получит пакет на свой адрес и не поймёт, какому внутреннему узлу его отдать. У GRE нет портов, поэтому пробрасывается весь протокол 47, а не порт.

**Где найти:** Firewall → NAT → Port Forward → Add (кнопка со стрелкой вверх - вставка правила в начало списка).

**Поля проброса:**

- **Interface:** WAN
- **Address Family:** IPv4
- **Protocol:** GRE (есть в выпадающем списке; поля портов при этом исчезают, у GRE их нет)
- **Source:** Advanced → можно оставить Any или указать WAN-адрес Linux-FW-2 (строже)
- **Destination:** WAN address
- **Redirect target IP:** внутренний адрес GRE-Linux-Client
- **Filter rule association:** Add associated filter rule (создаст разрешающее правило на WAN автоматически)
- **Description:** любое

Save, затем Apply Changes.

**Если создаёте правило на WAN вручную** (Firewall → Rules → WAN → Add):

- Action: Pass
- Protocol: GRE
- Source: WAN-адрес Linux-FW-2 (или Any)
- Destination: **внутренний адрес GRE-Linux-Client**, а не WAN-адрес pfSense. Правила WAN проверяются после трансляции DNAT, поэтому пакет уже имеет внутренний адрес назначения.

**Что ещё может мешать:**

- Interfaces → WAN: если WAN-адреса в лабе приватные, снимите галочки «Block private networks and loopback addresses» и «Block bogon networks», иначе пакеты будут отбрасываться.
- Исходящий GRE от клиента обрабатывается автоматическим Outbound NAT, отдельное правило не нужно. Это работает для одного туннеля через один NAT, чего в вашей лабе достаточно.

Проверка: Diagnostics → Packet Capture на WAN, протокол GRE. Если пакеты приходят, но не уходят на LAN, смотрите Status → System Logs → Firewall.

Пункт 5 нужен, чтобы обычные хосты сети 172.16.4.0/24 (и 172.16.2.0/24) отправляли трафик в удалённую сеть именно в GRE-узел, а не в интернет.

Сейчас хост из 172.16.4.0/24 шлёт всё на свой шлюз, то есть на pfSense-FW-2. У pfSense нет маршрута в 172.16.2.0/24, и он отправит пакет на WAN по маршруту по умолчанию, мимо туннеля. Экрану нужно указать, что 172.16.2.0/24 находится за GRE-Linux-Client. То же нужно сделать на Linux-FW-2 для сети 172.16.4.0/24.

**pfSense-FW-2:**

1. System → Routing → Gateways → Add: Interface = LAN, Gateway = LAN-адрес GRE-Linux-Client, любое имя. Save.
2. System → Routing → Static Routes → Add: Destination network = `172.16.2.0/24`, Gateway = созданный шлюз. Save, затем Apply Changes.
3. Firewall → Rules → LAN: должно быть правило, пропускающее трафик из 172.16.4.0/24 в 172.16.2.0/24. Обычно есть правило «allow any», но проверьте.

**Linux-FW-2:**

```
ip route add 172.16.4.0/24 via <LAN-адрес GRE-Linux-SRV>
```

В `iptables -A FORWARD` не должно быть правил, блокирующих трафик между этими сетями. Если по умолчанию FORWARD в DROP, добавьте разрешающее правило для `-s 172.16.4.0/24 -d 172.16.2.0/24` и обратное.

**Альтернатива:** вместо маршрутов на экранах можно прописать маршрут на каждом хосте сети (`ip route add 172.16.2.0/24 via <адрес GRE-узла>`). Для проверки достаточно одного хоста, а для всей сети удобнее маршрут на экране.

Проверка: с хоста из 172.16.4.0/24 выполните `ping` хоста из 172.16.2.0/24 и `traceroute`. В трассе должны появиться адреса туннеля 172.10.102.x.

Правило добавляется в цепочку FORWARD на Linux-FW-2, потому что трафик между сетями идёт транзитом через экран.

```
iptables -A FORWARD -s 172.16.4.0/24 -d 172.16.2.0/24 -j ACCEPT
iptables -A FORWARD -s 172.16.2.0/24 -d 172.16.4.0/24 -j ACCEPT
```
