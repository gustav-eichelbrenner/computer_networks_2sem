В linux есть iptables, nftables. Встраивается в сетевую подсистему ядра, позволяет управлять трафиком (разделенным на input и output). Этот фильтр позволяет блокировать трафик, reject (сообщать о блокировке трафика), пропускать трафик. Есть правила, по которым это делается - port, ip, protocol + input/output трафик.

forward трафик - переходящий. Не input и не output. Разница в том, что точно известен ip-адрес интерфейса в dest или src.

В iptables есть понятие цепочек. Помимо основного движка, который просто фильтрует, есть еще один, который занимается nat'тингом трафика. SNAT, DNAT, Masquerading. 

Pre-routing. Это когда трафик пришел на интерфейс, но еще не маршрутизировался.

Post-routing. Это когда трафик уже ушел. (48 минута)

Source NAT - меняет source-адрес.
Destination NAT - меняет dest-адрес. Работает на pre-routing'e.
Masquerading - (49 минута). Работает медленнее.

Есть механизм mangle. Позволяет подменивать параметры внутри ip-пакета. Можно менять TTL, размер ip-пакета и т.д.

На linux есть universal firewall (ufw). Примитивное решение. Лучше - pfsense.

У pfsense также есть engineering (фильтр). Смотрим только на input-трафик и только на интерфейс. Фильтрация - по ip port. Внутри же есть NAT. По сути, фильтр, NAT и Mangle в pfsense реализованы внутри одной штуки, похожей на blackbox. Смотрит только на входящий трафик на определенном интерфейсе. Правила относятся к интерфейсу. Сюда можно добавить IDS/IPS. Смотрит не только заголовок, но и тело (дату). Там сигнатурный анализ, по кусочкам. Есть сигнатурные правила. Правила для IDS/IPS и для fw могут быть разными.

iptables и pfsense - это сетевые firewall'ы. Работают на уровнях L3, L4 Osi.

Есть firewall'ы приложений. Смотрят на уровень L7 Osi (http, https).

# Видео "объяснение инфраструктуры и как с ней работать"

Внешние ip на fw - это белые ip. Тут помогает технология port forwarding в nat. Когда пакет доходит до внешнего ip, то fw может пробросить этот пакет/соединение до внутреннего ресурса с ip и портом. Это делается на сервере (а кто-то, кто обращается - тот клиент).

Публикация порта - внешний клиент получает возможность установить соединение с внутренним сервисом через адрес и порт роутера. Опубликовать порт = сделать внутренний сервис доступным извне через определенный порт внешнего интерфейса роутера. Более подробное объяснение - [[Проброс порта]]

Внутри туннелирования создается виртуальный интерфейс, чтобы система понимала, куда направлять трафик.
tun - это ip интерфейс, идет инкапсуляция трафика. Тут ip-ip туннель, все что ниже уровня L3 передать не получится.
tap - туннель на уровне L2, можно запихнуть фрейм. Это позволяет попасть во внутреннюю сеть, но чтобы это сделать, надо на свитче сделать bridge - сетевой мост. Получаем программный коммутатор.

чтобы Linux-машина роутила трафик, надо прописать systemctl net ipv4 port forwarding = 1. По умолчанию на линукс-машинках fw отключен, т.е. разрешает все. Это для tun-интерфейсов.

у tap-интерфейса есть подвох. Если сделать все то же самое, что и для tun-интерфейса, то можно связать внешний интерфейс и tap-интерфейс мостом, и тогда внутренняя и внешняя сети станут одной сетью, они будут связаны коммутацией.

nat работает на уровне L4 OSI. Очень понятно это объясняется на 41 минуте видео.

# Лекция №1 - Межсетевые экраны

**Зачем нужны межсетевые экраны?**
- Защита от внешних угроз (хакеры, вирусы, DDoS-атаки).
- Контроль за внутренними пользователями (предотвращение утечек данных).
- Разделение сетей (например, LAN и WAN).
- Обеспечение безопасности периметра сети.

**Основные функции межсетевых экранов:**
- Фильтрация трафика по IP-адресам, портам и протоколам.
- Блокировка нежелательных соединений.
- Логирование событий.
- Предотвращение вторжений (IDS/IPS).

# Видео лекции по межсетевым экранам

L4. Транспортный уровень. Предусматривает, что мы можем подключаться к разным сервисам одного и того же сервера (к разным сервисам, предоставляемым по одному и тому же ip-адресу). Выбираем, куда идет подключение и выбираем разные протоколы, чтобы реализовать разные виды подключений.

Протоколы L4. TCP, UDP, ICMP. У TCP и UDP есть абстракция портов. Позволяет подключаться к одному и тому же ip-адресу, но использовать разные сервисы.

Transmission Control Protocol. Пакет называется сегментом. ==MSS, MTU - разобраться==. TCP требует проверки от сервера, что отправленные данные дошли. Следующий пакет данных отправляется только после того, как был получен ответ.

Изначально никакого соединения нет, клиент знает ip сервера, а сервер слушает только tcp на определенном порту.
Когда приходит какой-то tcp-сегмент на определенный порт, то сервер отвечает клиенту и отправляет ему SYN-ACK пакет. Сервер ждет (у него timeout), пока клиент ответит.
Клиент получает SYN-ACK пакет, устанавливает соединение с сервером и уведомляет об этом сервер.
Это механизм тройного рукопожатия.

TCP может использоваться для ддоса систем, можно просто отправить очень много syn-пакетов.

User Datagram Protocol. Пакет называется датаграммой. Не требует подтверждения того, что данные дошли до сервера. Обычно используется для передачи данных, нечувствительных к небольшим потерям. Работает быстрее TCP.

Сервис - служба, которая запущена внутри сервака. Она слушает сеть какого-то протокола по какому-то порту.

У всех firewall'ов есть интерфейсы внутри и снаружи инфраструктуры.

Linux-firewall. Трафик может быть входящим или исходящим на интерфейс. В linux-системе есть технология ip forward, которая позволяет направлять input-трафик, по умолчанию он выключен, т.е. не передает трафик дальше. Его надо включить в параметрах ядра. Как его контролировать? Можно смотреть на входящий и исходящий трафик, а можно смотреть на трафик, который forward'ится. У Linux-машины есть 3 вида фильтров (по виду трафика) (рассматривается только iptables):
1. Input. Если destination является только эта linux-машинка (т.е. трафик не должен идти никуда дальше), то input будет работать.
2. Output. Если source является именно эта Linux-машинка (т.е. трафик исходит не от какого-то узла, который стоит за firewall'ом), то output будет работать.
3. Forward. Если трафик вида forward (т.е. конечный или начальный узел это не Linux-машинка, а что-то еще), то работоспособность трафика будет связана именно с ip forwarding в ядре Linux. Тогда будет работать только forward-трафик.
Можно смотреть по разным протоколам.

Второй вопрос - что можно сделать с трафиком перед тем, как его маршрутизировать и после того, как он маршрутизирован?
1. Если трафик приходит на интерфейс, то это PREROUTING.
2. Если трафик исходит из интерфейса, то это POSTROUTING.
На обоих этапах есть два вида цепочек.
3. NAT. На POSTROUTING'е можно поменять src-ip, сделаем классический NAT.
4. Mangle. Позволяет менять параметры внутри ip-пакета (так полагаю, не только заголовки вида src ip dest ip - ==разобраться==).

По крайней мере в iptables порядок правила определяет его приоритет. Верхнее (первое) правило является наиболее приоритетным. Второе - чуть менее приоритетным. И так далее. Если верхнее и нижнее правило конфликтуют, то будет выполняться верхнее правило.

Надо сидеть и очень хорошо разбираться в том, как работает firewall, ну в данном случае iptables.

pfsense контролирует только input-трафик. Нет никакого forward'а, не надо менять ip forwarding в ядре.

В этом плане iptables более навороченный и сложный, но позволяет гораздо объемнее контролировать трафик. А pfSense позволяет сильно быстрее работать.
