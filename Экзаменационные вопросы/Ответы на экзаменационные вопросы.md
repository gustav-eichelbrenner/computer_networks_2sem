## 🟢 1. Межсетевые экраны. Принцип работы

Межсетевой экран (firewall) — это программное или аппаратное решение, предназначенное для контроля и фильтрации сетевого трафика между различными сетями. Основная задача firewall — защитить внутреннюю сеть от несанкционированного доступа и атак извне. Фильтрует трафик по правилам. Правило = критерий + действие + счётчик. Нет критерия → правило на все пакеты. Нет действия → правило работает только как счётчик.

По умолчанию большинство firewall блокируют весь трафик, кроме явно разрешенного. Это политика "отказа по умолчанию".

Цепочка — упорядоченная последовательность правил. Цепочки можно разделить на пользовательские и базовые. Базовая - созданная по умолчанию при создании таблицы. Имена базовых цепочек всегда записываются в верхнем регистре (PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING). Имена пользовательских цепочек всегда должны записываться в нижнем регистре.

Таблица — совокупность базовых и пользовательских цепочек, объединенных общим функциональным назначением. При вызове команды iptables таблица указывается в формате -t имя_таблицы. При отсутствии явного указания, используется таблица filter.

Уровень работы: L3/L4 OSI (iptables, pfSense). Application firewall — L7 (http/https).

## 🟢 2. Виды межсетевых экранов

**Пакетные фильтры**
- Простейший тип firewall. Анализирует заголовки пакетов (IP-адреса, порты, протоколы). Не анализирует содержимое пакетов.
- Пример: iptables.

**Межсетевые экраны уровня приложений**
- Работают на уровне приложений (HTTP, FTP, SMTP). Анализируют содержимое пакетов.
- Пример: прокси-серверы.

**Прокси-серверы**
- Выступают посредниками между клиентом и сервером. Могут кэшировать данные и фильтровать запросы.
- Пример: Squid Proxy.

**Stateful Inspection Firewalls**
- Отслеживают состояние соединений (TCP, UDP). Анализируют контекст трафика (например, проверяют, был ли установлен SYN-пакет).
- Пример: pfSense, Cisco ASA.

## 🟢 3. Особенности работы iptables и pfSense FW

**iptables**:

- Интерфейс к Netfilter, ядро Linux ≥2.4, требует root. Позволяет администраторам создавать и изменять правила, управляющие фильтрацией и перенаправлением пакетов.
- Структура: таблицы (filter, nat, mangle, raw) + цепочки (PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING).
- Filter, NAT, mangle — раздельные таблицы/движки.
- Отслеживание состояний: NEW, ESTABLISHED, RELATED, INVALID.

**pfSense**:

- Основан на FreeBSD.
- Filter + NAT + mangle объединены в один блок, привязанный к интерфейсу, обрабатывает только входящий трафик интерфейса.
- Встроенный IDS/IPS: анализ тела пакета (сигнатуры), правила отдельные от firewall-правил.

## 🟢 4. Принципы настройки IPTABLES

- Таблица задаётся через `-t имя_таблицы`, по умолчанию — filter. Они создаются автоматически при работе с iptables
- Базовые цепочки — верхний регистр, пользовательские — нижний.
- filter: INPUT, FORWARD, OUTPUT — разрешение/блокировка.
- nat: PREROUTING, OUTPUT, POSTROUTING — только пакеты нового соединения; действия DNAT, SNAT, MASQUERADE, REDIRECT.
- mangle: 5 стандартных цепочек, модификация полей (TTL, TOS, MARK).

| Цепочка   | Что происходит                                                      | IP-пакет                                              |
| --------- | ------------------------------------------------------------------- | ----------------------------------------------------- |
| `INPUT`   | Пакет **пришёл на этот хост** и предназначен ему                    | `dst IP` — адрес этого хоста                          |
| `OUTPUT`  | Пакет **создан этим хостом**                                        | `src IP` — адрес этого хоста                          |
| `FORWARD` | Пакет **прошёл через этот хост**, который маршрутизирует его дальше | `src IP` и `dst IP` — обычно адреса **других хостов** |

## 🟢5. Принципы работы NAT. Настройка на Linux (iptables)

NAT реализуется через отдельную таблицу NAT, обрабатывающую только пакеты, открывающие новое соединение. Внутренний ip:port подменяется на внешний (белый) ip:port, имеется таблица соответствий для обратного преобразования.

Цепочки таблицы NAT:
- PREROUTING. Изменение dst-адреса до маршрутизации, DNAT.
- OUTPUT. Для локально генерируемых пакетов.
- POSTROUTING. Изменение src-адреса после маршрутизации - SNAT/MASQUERADE.

Действия:
- SNAT. Фиксированная подмена src-адреса, этап POSTROUTING.
- MASQUERADE. Вариант SNAT для динамического IP, определяет актуальный ip для каждого пакета.
- DNAT. Фиксированная подмена dst-адреса, этап PREROUTING.
- REDIRECT. Частный случай DNAT. Перенаправление на локальный адрес/порт.

Обязательное условие форвардинга между интерфейсами - включенный ip_forward.

Общий принцип настройки: `iptables -t nat -A <CHAIN> [criteria] -j <ACTION> [action parameters]`
- Настройка SNAT: `iptables -t nat -A POSTROUTING -o <out_int> -s <inner net/mask> -j SNAT --to-source <outer ip>`
- Настройка MASQUERADE: `iptables -t nat -A POSTROUTING -o <out_int> -s <inner net/mask> -j MASQUERADE`
- Настройка DNAT: `iptables -n nat -A PREROUTING -i <inner_int> -p <protocol number> ---dport <out_port> -j DNAT --to-destination <inner_ip>:<inner_port>`

## 🟢6. Принципы работы NAT. Настройка на pfSense

Принципы работы - как в 5 вопросе.

Filter, NAT, mangle не разделены на отдельные таблицы (как в iptables) — единый блок обработки, привязан к интерфейсу, смотрит только на входящий трафик.

- Outbound NAT (= Source NAT) в pfSense настраивается в **Firewall > NAT > Outbound**. Управляет заменой src-адреса/портов трафика, покидающего интерфейс.
- 4 режима:
    - **Automatic** (по умолчанию) — автоматическая генерация правил NAT для каждого напрямую подключённого интерфейса и сетей, достижимых через статические маршруты.
    - **Hybrid** — совмещение ручных правил с автоматическими для непокрытого ими трафика; наиболее гибкий режим.
    - **Manual (Advanced Outbound NAT)** — только вручную заданные правила, полный контроль, требует ручного сопровождения при изменении интерфейсов/подсетей.
    - **Disabled** — NAT отключён полностью (актуально, если все сети используют маршрутизируемые публичные адреса).
- Правила просматриваются сверху вниз, применяется первое совпадение.
- Outbound NAT не определяет, через какой интерфейс пакет покинет firewall — это задача таблицы маршрутизации

## 🟢7. Технология PortForwarding

Port forwarding = частный случай DNAT: входящее на внешний интерфейс соединение на заданном порту перенаправляется на внутренний IP:порт. Необходим, т.к. в дефолтной конфигурации NAT firewall не пропускает трафик, инициированный снаружи.

Порт-форвардинг имеет приоритет над локальными сервисами firewall (WebGUI, SSH) — если порт занят форвардом, локальный сервис фаервола на этом порту извне недоступен.

## 🟢8. Особенности использования Aliases в pfSense

Alias — именованная группа портов/хостов/сетей, на которую можно ссылаться в firewall-правилах, port forward, outbound NAT и др. Цель — сократить и упростить набор правил.

Firewall > Aliases. pfSense сам сортирует alias в нужную категорию по содержимому.

Типы алиасов: host, network, port, URL, URLTable, Built-In System Aliases.

Алиас может ссылаться на другие алиасы. Размер алиаса влияет на производительность, алиасы можно применять вне контекста firewall/NAT (например, в сервисах и диагностике).

## 🟢9. Настройка маршрутизации на Linux FW и pfSense

Linux FW:
- Транзитный (routing) трафик обрабатывается цепочкой FORWARD в таблице filter — требует включённого `net.ipv4.ip_forward`.
- Управление таблицей маршрутизации — через `ip route`:
    - Просмотр: `ip route show`
    - Маршрут по умолчанию: `ip route add default via <gw> dev <if>`
    - Статический маршрут: `ip route add <dst_net> via <gw> dev <if>`
    - Замена/удаление: `ip route replace ...`, `ip route del ...`
    - Постоянство после перезагрузки — только через конфиги дистрибутива (netplan, NetworkManager, `/etc/network/interfaces` и т.п.), сама команда `ip route add` не персистентна.

pfSense:
- Раздел **System > Routing**, вкладки Gateways / Static Routes / Gateway Groups.
- **Gateway** — узел, через который достижима удалённая сеть; создаётся до добавления статического маршрута (маршрут ссылается на существующий gateway, группы шлюзов для статического маршрута не допускаются).
- **Static Routes** — задаются только для сетей, недостижимых через интерфейс напрямую и недостижимых через default gateway; для local-сетей маршруты не нужны и могут вызвать проблемы.
- Outbound NAT в Automatic-режиме учитывает сети, добавленные через статические маршруты (автоматически формирует NAT-правила и для них).

## 🟢10. Протокол GRE. Особенности работы

**GRE (Generic Routing Encapsulation)** — туннельный протокол, инкапсулирует пакеты сетевого уровня внутрь виртуального point-to-point туннеля поверх IP-сети.

**Особенности:**

- Работает как отдельный IP-протокол — **номер протокола 47** в поле Protocol заголовка IPv4, не использует TCP/UDP. Чтобы работал GRE, необходимо, чтобы между концами туннеля уже была маршрутизация.
- Мультипротокольность — может нести практически любой протокол сетевого уровня в качестве полезной нагрузки.
- Структура: заголовок GRE (в котором указан тип инкапсулированного протокола) + инкапсулированный пакет.
- **Не шифрует трафик** — только инкапсуляция/туннелирование, нет встроенной защиты конфиденциальности → часто комбинируется с IPsec (GRE over IPsec) для защищённых туннелей.
- **Stateless** — не устанавливает сессию, не проверяет доставку (нет подтверждений/ретрансмиссий на уровне GRE).
- Увеличивает размер пакета (доп. заголовок) → возможна фрагментация, нужно учитывать MTU (типично снижают MTU туннеля до 1476 байт).
- Позволяет строить туннели между двумя точками через промежуточную (в т.ч. недоверенную/публичную) IP-сеть, скрывая внутреннюю адресацию/протоколы от транзитной сети.
- Поддерживает передачу маршрутной информации и мультикаст/broadcast-трафика через туннель — используется для организации динамической маршрутизации (OSPF, EIGRP) между удалёнными сайтами, что обычный IP-routing без туннеля не пропускает напрямую.
- Возможна рекурсивная инкапсуляция — требует контроля во избежание петель.

## 🟢11. Принцип работы протокола GRE

**Схема работы:**

1. На отправляющем узле исходный пакет оборачивается в заголовок GRE.
2. Получившийся GRE-пакет оборачивается в заголовок протокола доставки (delivery protocol) — обычно IPv4/IPv6: src/dst = адреса **туннельных интерфейсов** (публичные IP двух точек), протокол = 47.
3. Пакет маршрутизируется как обычный IP-пакет через промежуточную сеть до второй точки туннеля.
4. На принимающей стороне внешний IP-заголовок и GRE-заголовок снимаются, извлекается исходный payload-пакет.
5. Payload-пакет форвардится дальше по **его собственному** dst-адресу — используется таблица маршрутизации получателя; TTL payload-пакета декрементируется. Если dst payload-пакета совпадает с адресом отправляющего узла (что его инкапсулировал), то пакет отбрасывается (защита от петли).

## 🟢12. Особенности настройки протокола GRE на Linux

1. Необходима загрузка модуля `ip_gre` в ядро Linux с помощью команды `sudo modprode ip_gre`
2. Интерфейс `gre1` —обычный сетевой интерфейс с точки зрения ядра: на него можно назначить ip-адрес, добавлять в таблицу маршрутизации, включать в бридж
3. **MTU**: заголовок добавляет минимум 24 байта (20 IP + 4 GRE) → при MTU внешней сети 1500 внутренний MTU туннеля обычно выставляют **1476**. GRE не согласовывает MTU автоматически — задаётся вручную одинаково на обоих концах.
4. Настройка не персистентна по умолчанию — требуется сохранение через конфиги дистрибутива
5. При выходе трафика из туннеля во внешнюю сеть часто требуется SNAT/маскарадинг на туннельном интерфейсе

## 🟢13. Особенности настройки протокола GRE на роутерах Cisco

1. Настройка выполняется через создание логического Tunnel-интерфейса.
2. Tunnel source/destination ссылаются на адреса физических интерфейсов, а `ip address` на Tunnel-интерфейсе - отдельная логическая подсеть, созданная только для туннеля
3. Режим работы по умолчанию - `tunnel mode gre ip`
4. Опционально можно задать `keepalive` для point-to-point туннелей и `ip tcp adjust-mss` для компенсации дополнительных байтов GRE и предотвращения фрагментации TCP-сегментов.

## 🟢14. Особенности настройки протокола GRE на роутерах Mikrotik

1. **Создание интерфейса:** `interface gre add name=tunnel1 local-address=10.10.40.7 remote-address=10.10.50.8`. Параметр `remote-address` обязателен.
2. **IP на туннеле:** `ip address add address=172.10.101.1/30 interface=tunnel1 network=172.10.101.0`.
3. **MTU:** Автоматически = 1476 (1500 – 24 байта overhead). При необходимости: `mtu=1400` (например, для IPsec).
4. **Маршрутизация:** Маршрут через туннель: `ip route add distance=1 dst-address=192.168.4.2 gateway=172.10.101.2`.
5. **Ограничения RouterOS:** RouterOS плохо обрабатывает point-to-point на /32 маске.

## 🟢15. Особенности работы и настройки протоколов динамической маршрутизации при работе протокола GRE

1. **MTU:** обязательно уменьшить на обоих концах (обычно 1400–1476). GRE добавляет 24 байта overhead (4 GRE + 20 внешний IP). Без этого OSPF может зависать из-за фрагментации
2. **Keepalive:** включить (`keepalive=10s,10`), иначе при падении пира маршруты через туннель останутся в таблице, будет лишний трафик и якобы работающий маршрут.
3. **NAT-исключение:** если на WAN-интерфейсе есть masquerade, добавить `accept`-правило для GRE **выше** masquerade, иначе пакеты туннеля будут NAT-иться и он не поднимется.

## 🟡16. Принцип работы протокола GRE через NAT

**Проблема:** GRE — не TCP/UDP, а отдельный IP-протокол (номер **47**), у него **нет портов source/destination**. Классический NAT/**PAT** (Port Address Translation) различает несколько внутренних хостов за одним внешним IP **по TCP/UDP-порту** — для GRE такого идентификатора нет, поэтому обычный PAT «один внешний IP на много внутренних» с GRE напрямую не работает.

Последствия:
- **PAT (many-to-one)** не может мультиплексировать GRE-трафик нескольких внутренних хостов через один внешний IP — устройство не знает, какому внутреннему хосту вернуть ответный GRE-пакет.
- Одновременно через один NAT-роутер обычно может проходить GRE-трафик **только для одного** внутреннего хоста-туннеля
- Решение — **статический (1:1) NAT**, а не PAT: конкретный внутренний адрес однозначно транслируется в конкретный внешний, без разбора по портам. Тогда GRE-пакеты по протоколу 47 сопоставляются NAT-таблицей по IP-адресам напрямую.
- На межсетевом экране обязательно нужно явно разрешить прохождение **протокола 47** в правилах фильтрации

## 🟡17. Протокол OpenVPN. Особенности работы.

**OpenVPN** — открытый VPN-протокол/демон, реализующий защищённый туннель поверх обычной IP-сети. Не входит в стек IPsec, полностью самостоятельная реализация.

**Особенности:**

- **Работает в user space** (не встроен в ядро ОС), использует виртуальный сетевой интерфейс **TUN** (L3, IP-пакеты) или **TAP** (L2, Ethernet-кадры).
- **Криптография — через библиотеку OpenSSL**: наследует её TLS-инфраструктуру и шифронаборы.
- Два режима аутентификации/ключей:
    - **Static Key** — один заранее сгенерированный общий ключ на обе стороны, без TLS-согласования, только для простых point-to-point сценариев.
    - **SSL/TLS mode** — полноценный TLS-handshake с клиентскими/серверными сертификатами, поддержка множества клиентов, согласование сессионных ключей, возможность отзыва сертификатов.
- **Транспорт — TCP или UDP** (порт по умолчанию 1194); UDP предпочтителен (ниже задержки, нет двойного TCP-over-TCP retransmit при потерях), TCP — для обхода строгих фаерволов/прокси.
- Может проходить через **NAT и прокси-серверы** без дополнительных ALG — благодаря работе поверх обычного TCP/UDP.
- Поддерживает **динамические IP клиента и DHCP**, масштабируется до сотен-тысяч одновременных клиентов (сервер + множество клиентов, а не только point-to-point).
- Кроссплатформенность — работает на большинстве ОС
- Поддерживает **сжатие трафика**, keepalive/переподключение, push-конфигурацию клиенту с сервера

## 🟡18. Принцип работы протокола OpenVPN L3

Режим **TUN** — работа на сетевом уровне (**L3**), туннелируются **IP-пакеты**, а не Ethernet-кадры.

**Принцип:**

1. На клиенте и сервере поднимается виртуальный интерфейс **tun0**, которому назначается IP из отдельной туннельной подсети.
2. Исходный IP-пакет от приложения попадает в таблицу маршрутизации узла и направляется в `tun0`
3. OpenVPN-демон забирает пакет из `tun0`, **шифрует и инкапсулирует** его в OpenVPN-пакет (TLS-сессия), оборачивает в UDP/TCP и отправляет через физический интерфейс на адрес удалённой стороны.
4. На принимающей стороне пакет расшифровывается, из него извлекается исходный IP-пакет, который инжектируется в `tun0` получателя и дальше обрабатывается обычной IP-маршрутизацией

## 🔴19. Принцип работы протокола OpenVPN L2

Режим **TAP** — работа на канальном уровне (**L2**), туннелируются **Ethernet-кадры**

**Принцип:**

1. На клиенте и сервере поднимается виртуальный интерфейс **tap0**, эмулирующий обычную Ethernet-карту.
2. `tap0` включается в локальный bridge вместе с физическим LAN-интерфейсом узла — туннель становится логическим продолжением локального Ethernet-сегмента.
3. Любой кадр, приходящий в локальный сегмент, через бридж попадает в `tap0`.
4. OpenVPN-демон забирает Ethernet-кадр из `tap0`, **шифрует и инкапсулирует** его в OpenVPN-пакет (TLS-сессия), оборачивает в UDP/TCP и отправляет удалённой стороне.
5. На принимающей стороне кадр расшифровывается и инжектируется в `tap0` получателя, откуда через локальный bridgr попадает в LAN-сегмент получателя — как будто кадр физически пришёл по Ethernet-кабелю.

Для справки (на бумаге не писать): локальный сегмент - он же broadcast-домен - часть сети, в которой все устройства соединены на L2 OSI и видят трафик друг друга без маршрутизации. Локальный bridge - виртуальное сетевое устройство, которое объединяет несколько сетевых интерфейсов узла в один L2-сегмент; технически - отдельный виртуальный интерфейс, к которому привязываются два и более физических/виртуальных интерфейса. Локальный bridge разворачивается между eth0 и tap0
